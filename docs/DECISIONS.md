# Decisions Log

Running log of decisions made autonomously per `PROMPT.md` §0, with the "why."

- **Fonts:** Heebo (Hebrew) + Inter (English), loaded via `next/font/google`, variable fonts `--font-heebo` / `--font-inter`. Reasoning: Heebo was designed to sit well alongside Latin grotesque sans fonts, and Inter is the de facto premium-SaaS English face (Linear/Vercel-adjacent). `html[lang]` switches which is primary via `app/globals.css`.
- **Package manager:** npm, matching the `npm run ...` commands specified in §17/§18.
- **Stack versions:** Next.js 16.4.5 (App Router, Turbopack), React 19.3, Tailwind CSS 4.3 (CSS-first `@theme` config, no `tailwind.config.ts`), TypeScript 5 strict. All latest stable at build time.
- **i18n routing:** `next-intl` v4 with `localePrefix: "always"` — `/he` and `/en` both always show a prefix, `/` 307-redirects to `/he` (default locale) via middleware. File-based routing conventions in `i18n/routing.ts`, `i18n/request.ts`, `i18n/navigation.ts`.
- **Middleware → Proxy:** Next.js 16 deprecated the `middleware.ts` convention in favor of `proxy.ts` (same API). Renamed accordingly to avoid the build-time deprecation warning.
- **Unit test runner:** Vitest (not specified in the stack list) chosen for `lib/savings.ts` unit tests — fast, zero-config with Vite/Turbopack-era tooling, first-class TypeScript support. Playwright remains the E2E/visual/axe runner as specified.
- **Variant styling:** Added `class-variance-authority` and `@radix-ui/react-slot` (small, standard, widely-used primitives) to keep Button/Card/Badge variant logic declarative instead of hand-rolled conditionals, given the number of component states required by §5.4.
- **CSP:** `script-src`/`style-src` include `'unsafe-inline'`. A strict nonce-based CSP would require per-request nonce wiring through the `next-themes` no-FOUC script and Next's hydration script; given this is a marketing site (no user-generated script content, no third-party ad scripts), the pragmatic documented tradeoff is `unsafe-inline` rather than a brittle nonce pipeline. Revisit if a stricter policy is required before launch.
- **Analytics:** Wired behind `NEXT_PUBLIC_ANALYTICS_ENABLED` env var (default off) and gated further by cookie-consent state at runtime, per §13. No analytics provider is actually integrated yet — this is a hook point only.
- **qa/ screenshots:** Generated locally by the Playwright visual-QA pass (§18.2) but git-ignored (binary bloat); regenerate anytime with the QA script documented in the final report.
- **Contact form rate limiting:** `app/api/contact/route.ts` uses a basic in-memory per-IP counter (5 requests / 10 min), matching §12's "rate limiting בסיסי". This resets per server instance, so on a multi-instance serverless deployment it's a soft deterrent, not a hard guarantee — swap in a durable store (e.g. Upstash Redis) before relying on it under real spam load.
- **Contact "no fake success":** verified end-to-end — with `WEBHOOK_URL` unset, the form shows `errors.noWebhook` and keeps the user's entered values intact (no silent data loss) instead of a fake success state, per §12.
- **Dynamic OG image RTL text:** Satori (the renderer behind `next/og`'s `ImageResponse`, used for §14's dynamic `opengraph-image`) has no bidi algorithm — it laid out Hebrew text character-by-character left-to-right, rendering every word mirrored. Fixed via `lib/bidi-fix.ts` (reverse the string, then re-reverse embedded Latin/digit runs back to normal — the standard workaround for bidi-naive renderers). Multi-line auto-wrapped strings additionally invert line order under this trick, so the Hebrew OG headline/description are pre-split into short manual lines (reusing the Hero's own line breaks, split at the description's natural comma) and each line is bidi-fixed independently rather than fixing one long auto-wrapping string. Verified visually — both locales render correctly.
- **i18n middleware matcher:** `proxy.ts`'s matcher originally only excluded paths containing a dot (for static files like `/robots.txt`), which missed Next's extension-less dynamic-icon routes (`/icon`, `/apple-icon`) — they were being redirected to `/he/icon` (404) by the locale middleware. Fixed by excluding them explicitly in the matcher. Found via Playwright, not manual testing — worth remembering that any future root-level special route needs the same exclusion.
- **Lazy loading (§14):** The site has no raster images (all decoration is SVG/CSS), so there was nothing to `loading="lazy"`. Below-the-fold sections already defer their *animations* via Motion's `whileInView`, but are still SSR'd in full (not `next/dynamic`-code-split) so their text content is present in the initial HTML for SEO/LCP — a deliberate tradeoff of JS-bundle size for crawlability on a content-light page.
- **Hero subtitle LCP regression (real finding, not theoretical):** Lighthouse mobile (real `devtools` throttling, 4x CPU) measured LCP at 4.4s against the spec's 2.5s budget — failing it. The LCP element was the Hero subtitle paragraph, which started at `opacity:0` and faded in via Motion with a 0.5s delay; under real mobile CPU throttling that JS/rAF-driven fade pushed its actual paint out by ~4.4s (simulated throttling in Lighthouse's default `--preset=perf` run had hidden this — it models network/CPU from a dependency graph and did not catch it, so `--throttling-method=devtools` was needed to see the real number). Fixed by making the subtitle a plain static `<p>` (not Motion-animated — it isn't one of the spec's explicitly-required animated elements, unlike the H1's word-by-word reveal) and tightening the rest of the Hero's entrance-animation delays (0.5–0.75s → 0.15–0.35s). Result: mobile LCP 4.4s → 1.6s, Performance 84 → 99. Lesson for any future above-the-fold copy: don't gate a likely-LCP text block's initial visibility behind a JS animation library, and verify Lighthouse mobile numbers with real throttling, not just the simulated default.
